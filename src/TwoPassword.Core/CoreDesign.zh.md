# 2Password 核心：格式 V1

[English](CoreDesign.md) · [简体中文](CoreDesign.zh.md)

本文件描述 `TwoPassword.Core` 实现的初始 **V1** 格式。它在包内保存经过认证的加密内容和可选的 PAR2 恢复数据。应用只写入和读取这一种格式。

## 依赖与数据流

- 密钥派生：`Konscious.Security.Cryptography.Argon2` 1.3.1。
- AES-256-GCM 和 SHA-256：.NET `System.Security.Cryptography`。
- 归档序列化：.NET `System.Formats.Tar`，使用 PAX 格式。
- 独立块压缩：`ZstdSharp.Port` 0.8.8（Zstandard 1.5.7 的实现）或 .NET Brotli。默认使用 Zstd。
- Windows 路径、数据流、时间戳和 ACL：.NET 文件系统 API，以及用于卷能力、原子创建目录和数据流枚举的公开 Windows API。

创建时，文件数据以流式方式写入 PAX TAR，填充最多 1 MiB 的明文块，按需压缩该块，再将它加密。不会写出明文中间 TAR 文件。完成后的**加密**临时载荷交给可选的恢复记录写入器，再根据载荷和恢复数据的长度决定使用内嵌 EXE 还是分离数据文件。

解码按相反顺序进行，每次处理一个已经认证的数据块。应用的正常路径先认证并解包，因此完整数据只需读取一遍。遇到与损坏有关的失败时，恢复层使用内嵌 PAR2 数据修复一份位于私有工作区的载荷副本，再从副本解包。显式的预检查选项会先使用恢复数据核对整个载荷。密码语法无效时，在恢复工作开始前拒绝；所有密钥槽都不识别的密码会单独报告，不会自动触发开销较大的扫描。错误密码与密钥数据损坏仍无法区分，因此怀疑密钥数据损坏的用户可以主动请求恢复检查。核心不做尽力而为的部分解包：只有完整归档和经过认证的终止块都验证通过后，才会发布目标目录。

## 独立密码

一个容器有 1–16 个互不相同的密码，每个密码都可以是空字符串。存在空密码槽时，即使其他槽的密码不为空，任何人也能用空输入解包。空密码槽与其他槽使用相同的密钥派生和认证加密。密码长度上限为 1024 个 UTF-16 代码单元；拒绝 null 字符串和无效代理项序列。空密码列表和重复密码（包括两个空字符串）都会被拒绝。

V1 将**每个**密码槽的 Argon2id 输入定义为 `0x00 || StrictUTF8(password)`。字符串从不去除首尾空白，也不进行归一化。固定前缀使空字符串也能成为依赖库接受的非空字节输入，同时不会混淆不同密码：空字符串编码为 `00`，单个 U+0000 字符编码为 `00 00`。

每次创建都会生成新的随机 32 字节内容密钥。每个密码使用新的 16 字节盐和固定参数，通过 Argon2id 独立派生一个 32 字节的密钥加密密钥：

- 内存：65,536 KiB。
- 迭代次数：3。
- 并行度：4。

每个密钥槽包含盐（16 字节）、随机 GCM nonce（12 字节）、包装后的内容密钥（32 字节）和认证标签（16 字节）。槽的附加认证数据（AAD）由固定的 48 字节逻辑包头和紧随其后的 32 位小端槽索引组成。

包内从不保存密码字符串及其派生密钥。知道一个密码，就能按设计获得内容密钥和归档；它不会从数学上推导出另一个密码。其他弱密码仍可被离线猜测。因此，内容访问的安全性取决于最弱的授权密码。

## 逻辑包头

除非另有明确说明，下列整数均采用小端序。

| 偏移 | 字节数 | 值 |
|---:|---:|---|
| 0 | 8 | ASCII `2PWPKG01` |
| 8 | 4 | 版本 = 1 |
| 12 | 4 | 原始块大小 = 1,048,576 |
| 16 | 1 | 请求的编解码器：0 = 无压缩，1 = Brotli，2 = Zstd |
| 17 | 3 | 保留，必须为零 |
| 20 | 8 | 源文件总字节数 |
| 28 | 4 | 文件数量 |
| 32 | 4 | 目录数量 |
| 36 | 4 | 随机 nonce 前缀 |
| 40 | 4 | 密码槽数量 |
| 44 | 4 | 保留，必须为零 |
| 48 | 76 × 槽数量 | 独立密钥槽 |

文件名和 PAX 元数据位于加密块中。文件/目录数量、数据总长度、压缩选项和密码槽数量属于公开的包头元数据。

逻辑包头的 SHA-256 是包头身份标识，包含在每个数据块的 AAD 中。不可信文件无法任意指定 KDF 内存、迭代次数、算法或分配大小。

## 包头冗余存储

载荷起始处是三个完全相同的 2048 字节记录，共占固定的 6144 字节区域。每条记录包含：

| 偏移 | 字节数 | 值 |
|---:|---:|---|
| 0 | 8 | ASCII `2PWHDR01` |
| 8 | 4 | 逻辑包头长度 |
| 12 | 4 | 保留，必须为零 |
| 16 | 32 | 逻辑包头的 SHA-256 |
| 48 | 可变 | 逻辑包头 |
| 剩余部分 | 可变 | 用零填充至 2048 字节 |

读取器需要至少一条完整且校验通过的记录。如果多条校验通过的记录内容不一致，就拒绝整个包。校验值只用来选出完整副本，不能代替认证。在开始任何明文暂存之前，所选逻辑包头还必须通过加密内容的认证。

## 独立认证的数据块

每个块独立压缩，块之间不共享压缩字典。如果压缩会使块变大，该块就使用编解码器 0。

| 字段 | 字节数 | 含义 |
|---|---:|---|
| 原始长度 | 4 | 数据块为 1–1,048,576 |
| 编码长度 | 4 | 数据块为 1–原始长度 |
| 编解码器 | 1 | 0，或全局选择的编解码器 |
| 保留 | 3 | 必须为零 |
| 密文 | 编码长度 | 由 AES-256-GCM 加密的原始/压缩字节 |
| GCM 标签 | 16 | 认证标签 |

编解码器 0 要求原始长度与编码长度相等。压缩块必须小于其原始长度。终止块具有全零的 12 字节记录头，没有密文，并带有有效的 16 字节标签。

12 字节 nonce 由包头中的随机 4 字节前缀和紧随其后的 64 位**大端**递增块索引组成。AAD 由以下部分组成：

1. 逻辑包头 SHA-256（32 字节）。
2. 64 位大端块索引（8 字节）。
3. 完整的 12 字节块头。

52 字节的 AAD 绑定块长度、编解码器、保留位、顺序，以及逻辑包头和密钥槽的全部字节。必须存在经过认证的终止块，并精确检查载荷结束位置，从而拒绝截断、丢弃/重排/重复记录及额外记录。

### 编解码器限制

Brotli 写入时使用质量等级 6 和 1 MiB 窗口。每次解码必须恰好生成预期数量的字节，并恰好消耗认证后的整个编码块；额外或截断的压缩数据会导致失败。

Zstd 使用等级 3、最大 1 MiB 窗口和帧校验值。解码前，由受维护的 Zstandard 解析器验证：只有一个标准帧、字典 ID 为 0、声明内容长度准确、窗口大小受限，以及压缩帧边界准确。解码使用调用方提供的固定大小 span，绝不按照帧声称的输出大小分配内存。

一个小型、隔离的 unsafe 包装层会固定这些有界 span，以调用 ZstdSharp 中受维护的帧解析方法。它不进行指针运算或非托管内存分配。

## 冗余尾部

物理文件以三条 64 字节尾部记录结束（总计 192 字节）：

| 偏移 | 字节数 | 值 |
|---:|---:|---|
| 0 | 8 | ASCII `2PWTAIL1` |
| 8 | 8 | 载荷起始偏移 |
| 16 | 8 | 载荷长度：包头副本和数据块 |
| 24 | 8 | 恢复数据长度，没有时为零 |
| 32 | 32 | 前 32 字节的 SHA-256 |

载荷偏移 + 载荷长度 + 恢复数据长度 + 192 必须等于文件长度。至少要有一条校验有效的记录；有效记录相互冲突时拒绝处理。最后一个经过认证的块必须恰好结束于载荷末尾。内嵌 EXE 的载荷偏移是解密程序模板的长度；原始 `.2pw` 数据文件使用偏移零。物理布局如下：

- 内嵌 EXE：`[stub][payload][recovery][footer]`。
- 数据文件（`.2pw` 或原始容器）：`[payload][recovery][footer]`。

冗余最多容忍两份包头副本和两份尾部副本损坏。它不会重建损坏的密文，重建由恢复区域负责。全部尾部副本丢失时，恢复层仍可定位这些区域；参见[尾部丢失](#尾部丢失)。

## 内嵌恢复数据

恢复区域由 par2cmdline-turbo 1.5.0 为单个名为 `payload` 的源文件生成的 PAR2 文件拼接而成，该源文件的字节与载荷完全相同。文件按文件名的序数顺序拼接，因此索引文件排在最前。创建时运行 `par2 c -r<percent> -B<work> -- <work>\payload.par2 <work>\payload`，不附加其他选项，以保留 par2 的默认值：

- 块大小：约 2000 个源块；载荷长度为 `S` 时，块大小为 `roundup4(max(ceil(S / 2000), 4))`。
- 恢复文件大小逐个翻倍，每个文件都重复保存关键包。
- 内存和线程数由 par2 决定。

默认冗余为 5%；GUI 和 CLI 还提供 10%、20% 和关闭选项。由于关键包会重复，小载荷也有固定开销：5 MiB 载荷在 5% 冗余下会产生约 1.4 MB 的恢复数据。拼接后的输出必须通过与修复时相同的验证器才会被接受。如果生成失败（例如卷不支持持久 ACL），仍会发布不带恢复数据的包，并报告错误。取消则会取消整个创建操作。

读取器从不信任恢复区域的结构。`Par2Metadata` 逐包扫描，只接受以下包类型，且每种类型的长度必须精确符合要求：Main（92 字节）、FileDesc（128 字节）、IFSC（80 + 20 × 数据片数量）、RecvSlic（68 + 块大小）和 Creator（68 至 1088 字节）。包头损坏时，通过搜索下一个 `PAR2\0PKT` 标记跳过该包；MD5 校验失败时，从该包起点之后 8 字节处继续扫描。参与哈希计算的数据总量上限为恢复区域长度的两倍加 64 MiB。随后要求：

- 恰好一个恢复集，Main 包的哈希与恢复集 ID 相符，使用默认块大小且只包含一个文件；
- 该文件 ID 恰好对应一个 FileDesc，名称为 `payload`、长度为载荷长度，并且 FileID 哈希匹配；
- 恰好一个 IFSC 表；
- RecvSlic 指数小于 65535，并去重。Creator 包会被丢弃。

检查时，逐片计算载荷的哈希（最后一片补零至块大小），并将 MD5 与 IFSC 表比较。退出码为：0 表示完整，1 表示可修复，2 表示恢复块不足，4 表示没有可用恢复数据。

修复以 `FileShare.Read` 打开数据文件供写入，将载荷复制到私有工作区，并只将已验证的包写入 `payload.par2`，复制时逐包再次校验。随后运行 `par2 r -B<work> -- <work>\payload.par2`，检查每个数据片和整个载荷的 MD5，再只将损坏的数据片写回原位置。因损坏触发的解包会在目标位置旁的工作区修复一份副本，给它添加尾部 `(0, length, 0)`，使其成为原始数据容器，然后从副本解包；包文件本身不会改变。

没有载荷数据片损坏时，检查和修复也会在接受结果或替换尾部前验证完整的 V1 逻辑包头。原生工具重建之后，必须先验证还原出的 V1 包头，才能写回任何数据片。分离数据还必须与启动器中的逻辑包头身份标识一致。

### 尾部丢失

三条尾部记录彼此相邻，因此一个坏扇区或文件截断就可能让它们全部丢失；尾部也不在 PAR2 覆盖范围内。`LocateRegions` 因 `PackageException` 失败时，恢复层会从文件本身重建区域信息：

1. 候选载荷起点。如果启动器的 `2PWLINK1` 尾部仍然校验通过，它会指向从偏移 0 开始的数据文件。否则，`FindHeader` 向前扫描 `2PWHDR01`，返回首条长度、保留字段、SHA-256 和零填充都验证通过的记录；EXE 模板可能将该魔数作为常量包含在内，因此仅找到魔数还不够。三份副本相同且不带索引，因此在 `h` 处命中时，候选起点是 `h`、`h − 2048` 和 `h − 4096` 中非负的位置。没有有效记录时，唯一候选起点为 0。
2. 载荷长度。`FindSourceLength` 从文件末尾向前搜索 FileDesc 包，要求其 MD5 校验通过、名称为 `payload`，且 FileID 匹配。par2 在每个恢复文件中都重复写入该包，因此靠近文件末尾也有副本。
3. 恢复集。`Par2Metadata.Read` 扫描 `[lowest start + length, end of file)`，记录该恢复集中最后一个完整包的结束位置。标记重同步最多会跳过开头的 4096 字节载荷数据。
4. 起点。对每个候选起点，从包头副本之后到最后一片之间分散选取最多 16 个数据片（数据片超过 4 MiB 时，最少只选 2 个），计算哈希并与 IFSC 表比较；全零的数据片会被跳过。匹配数最多且至少有一次匹配的起点胜出。如果初始样本全部没有匹配，就在所有候选起点上继续检查其他非零数据片，最多增加 `RecoveryBlocks + 1` 个不同的数据片，或检查完可用数据片，直到找到匹配。无论 PAR2 块大小是多少，样本哈希计算都使用固定的 1 MiB 缓冲，包括补零处理。恢复区域从载荷末尾延伸到最后一个完整包的末尾。

随后，即使载荷完整，检查也会报告退出码 1。修复先还原损坏的数据片，再在最后一个完整包之后截断文件，并为重建的区域写入新尾部。从尾部丢失的文件解包时，会将载荷复制到工作区（必要时修复），再从副本解包。文件截断到载荷内部时，已经没有 PAR2 数据，因此仍会失败。应用通过尾部魔数识别内嵌 EXE，因此三份魔数全部丢失的 EXE 会作为普通 2Password 打开；请用另一份程序修复它。

## 自动与分离布局

`CreateOptions.Layout` 支持：

- `Auto`：当模板 + 载荷 + 恢复数据 + 尾部不超过 4,294,967,295 字节时，将完成的载荷内嵌；否则创建一个较小的 EXE 和同目录的 `.2pw` 数据文件。
- `Embedded`：要求生成不超过上述限制的单个 EXE。
- `Detached`：始终创建一个较小的 EXE 和同目录的 `.2pw` 数据文件。

分离布局要求调用方提供自包含的解密程序模板。没有模板的 `Auto` 创建会写出原始容器。GUI 使用自身发布的独立可执行文件作为模板。

分离 EXE 只包含解密程序模板和引用描述。描述保存为三份 2048 字节副本，加上三条 64 字节尾部记录，引用总开销为 **6336 字节**。同目录的数据文件从偏移零开始保存完整 V1 信封，包括恢复数据，因此分离包始终恰好由两个文件组成。

逻辑引用描述：

| 偏移 | 字节数 | 值 |
|---:|---:|---|
| 0 | 8 | ASCII `2PWREF01` |
| 8 | 4 | 文件名字节长度 |
| 12 | 4 | 保留，必须为零 |
| 16 | 32 | 预期的数据文件逻辑包头 SHA-256 |
| 48 | 可变 | 使用严格 UTF-8 编码的同目录文件名 |

引用记录的魔数是 `2PWLHDR1`；引用尾部的魔数是 `2PWLINK1`。其余记录和校验值布局与上文相同。引用尾部指向 6144 字节的描述区域，其恢复数据长度必须为零。

文件名必须是以 `.2pw` 结尾的单个有效 Windows 文件名，最多 255 个 UTF-16 代码单元、1024 个 UTF-8 字节。绝对路径、分隔符、路径穿越、设备名、ADS 语法、无效 Unicode 和重解析点父目录均会被拒绝。读取器在尝试密码派生之前核对预期包头哈希。引用不能递归串联。数据文件也可以不经启动器直接打开。

创建时，先发布完成的数据文件，最后发布启动器，两者都不覆盖已有文件。失败时只删除属于本次操作的临时文件或新发布文件。两次重命名之间崩溃可能留下孤立的加密数据文件。

## 文件系统与归档不变量

PAX 名称使用严格 UTF-8。不进行 NFC、NFD、NFKC、大小写或其他归一化。文件内容始终视为不透明字节，包括使用 GBK、Shift-JIS 或无效文本编码的文件。

源根目录或根文件本身也是一个归档条目。空文件/目录、隐藏和系统文件、精确名称、完整内容、创建/写入时间戳及支持的 Windows 基本属性都会保留。`Zone.Identifier` 按原始字节保存，每个条目最多 64 KiB。其他备用数据流、重解析点、目录联接、符号链接、EFS、设备和离线条目都会明确拒绝，不会静默丢失。

应用使用的 PAX 字段：

| 字段 | 编码 |
|---|---|
| `2Password.creationTicks` | 使用固定格式的十进制 UTC `DateTime.Ticks` |
| `2Password.writeTicks` | 使用固定格式的十进制 UTC `DateTime.Ticks` |
| `2Password.attributes` | 允许属性的十进制位掩码：ReadOnly、Hidden、System、Archive、NotContentIndexed |
| `2Password.zoneIdentifier` | 可选，精确原始 ADS 字节的 base64 |

在 BCL 归档读取器能按不可信长度分配内存之前，帧边界检查层会将每条 PAX 元数据记录限制为 256 KiB 和 64 个互不重复的字段。只接受标准 PAX 普通文件/目录条目。该层会强制执行经过认证的文件字节预算，并要求恰好有两个全零 TAR 终止块。

源扫描包含所有条目，遇到无法访问的条目就失败。文件以 `FileShare.Read` 打开，复制期间不允许并发写入和删除。前后清单检查会检测名称、大小、时间戳、属性及 Zone.Identifier 内容的变化。由于没有 VSS 快照，同一用户下的进程与这些检查竞态执行时，仍有可能得到多个文件之间不一致的归档。

解包拒绝路径穿越、绝对路径、无效/设备名称、重复路径、大小写不敏感的冲突、缺失的父目录、不支持的类型、超大元数据及不一致的认证总量。它只在目标父目录下的随机私有暂存目录中创建新文件，认证整个数据流、还原元数据，最后以不覆盖方式重命名目录。

创建暂存目录之前，共享的 `WindowsPrivateDirectory` 辅助类会打开已有父目录，并要求实际卷报告 `FILE_PERSISTENT_ACLS`。能力查询不可用或卷不支持持久 ACL 时，会在写入任何明文文件前失败。原生 `CreateDirectoryW` 原子地设置受保护的 DACL，并拒绝已有路径。辅助类读回原始安全描述符，要求所有者为当前用户、存在且受保护的 DACL，并且恰好包含分别授予当前用户和 SYSTEM 完全控制的两个 Allow ACE，带有对象/容器继承且没有额外 ACE。验证失败时，只尝试删除本次新建的空目录，绝不删除意外出现的目录树。恢复工作区使用相同的辅助类。

本地 NTFS 是经过验证的目标文件系统。FAT32 和 exFAT 缺少持久 ACL，不能用作解包目标或恢复工作区。网络文件系统只有在提供程序能报告所需能力，并保留精确验证过的 DACL 时才会被接受。源数据流枚举正常处理 EOF；只有成功查询卷能力并确认没有 `FILE_NAMED_STREAMS` 后，才将错误 1/50/87 视为不支持数据流。查询失败，或提供程序声称支持数据流却拒绝枚举时，都会明确失败。这些检查使用公开的[卷能力标志](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-getvolumeinformationbyhandlew)。

暂存/最终目录保留上述私有 ACL。不会重现原始 ACL、所有者、EFS 身份、硬链接关系、NTFS 压缩/稀疏布局，以及 Zone.Identifier 以外的 ADS。稀疏输入的字节会精确保留，但还原文件可能占用其全部逻辑大小对应的空间。

## 资源与操作边界

- 每块原始/解压数据：最多 1 MiB。
- 未压缩的主文件内容总字节数：最多 16 TiB；这不是密文输出大小的限制。
- 条目数量：最多 1,000,000，同时受下述元数据预算约束。
- Windows 完整/相对路径：少于 32,700 个 UTF-16 代码单元；每个路径分量最多 255 个。
- 保守的保留元数据预算：每份源清单 128 MiB（前后清单可能同时存在），解包 256 MiB。待处理的目录枚举会在保留前计入预算。超过预算时明确失败。
- 自包含 EXE 上限：4,294,967,295 字节，包括恢复数据。较大的加密数据使用分离布局。
- 编码、加密、解码、复制和哈希计算均以流式方式进行。临时载荷始终加密。组装内嵌 EXE 时暂时需要第二份加密副本，生成恢复记录时需要一个临时恢复文件。
- 从不覆盖目标文件或目录。
- 正常失败/取消会通过普通删除清理临时输出。强制终止进程或断电可能留下私有暂存目录或加密临时文件。
- 同一用户下已被攻陷的进程、恶意 EXE 模板、键盘记录器、内存转储或被替换的可执行文件，不在数据加密威胁模型内。AEAD 只认证加密数据文件；可执行程序模板的信任来自签名与分发。
